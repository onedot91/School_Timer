# 학생 저장 신뢰성 개선 적용 결과

확인일: 2026-09-09. 운영 사이트: https://school-timer-five.vercel.app/

## 운영 적용

1. Supabase `classword_command_v2(integer,text,text,jsonb,integer)` 함수 한 곳을 변경했다. 기존 함수 해시가 일치할 때만 적용하도록 제한했고, 트리거·실행 권한·학생 기록·잔액을 변경하는 SQL은 실행하지 않았다.
2. 서버 호환 변경 `24650371103f4301bcca8f9d05e49f9a0c3e8ceb`을 먼저 배포했다.
3. 클라이언트 및 회귀 검증 `124698d88dcaf3d4a064e8df1a92d75ab7dc7b8b`을 배포했다.
4. 운영에서 보호 정보 없는 구버전 저장을 거절하는 설정 `24d660a04edb8dd31127174577d451f89a7c6e30`을 배포했다.

세 커밋 모두 GitHub의 Vercel 상태가 success인 것을 확인했다. 최종 운영 `/api/shared-settings` 응답 헤더는 `X-Storage-Edit-Revisions: required`, 리전은 `icn1::icn1`이었다. 인증 없는 확인 요청의 HTTP 401은 정상적인 기기 인증 거절이다. 실제 인증된 운영 학생 화면도 열렸으며, 해당 탭의 수집된 오류 로그는 0건이었다. 운영 학생 화면에서 테스트 글이나 가상 거래를 제출하지 않았다.

Supabase 함수의 변경 후 정의 해시: `7d636b71f50d8b40b614d7cadc59757e`. transportHash와 문항 컨텍스트 검사가 존재하며, 기존 `postgres` / `service_role` 실행 권한 및 security definer 설정을 유지한다.

## 확인한 결함과 수정

- 이전 저장 응답이 나중에 작성한 초안을 삭제하던 경로: 편집 버전과 제출 요청을 분리하고 조건부 정리한다.
- 초안 교체 중 기기 저장 실패: IndexedDB 트랜잭션, 원래 요청 ID를 유지하는 이전, 메모리 보관·복사·화면 이탈 보호를 적용했다.
- 저장 영수증 확인이 화면 조회 실패에 영향을 받던 경로: 영수증 독립 조회와 `저장됨 · 화면 갱신 중`을 분리했다.
- 이미 저장된 요청의 재검증이 거짓 실패를 만들던 경로: 영수증 재확인과 같은 ID 재시도, 사용자·내용 해시 확인을 추가했다.
- 오래된 게임 입력과 조회 응답이 새 입력을 덮던 경로: revision 및 응답 세대 검사, 최신 입력 보관, 명시적인 충돌 확인을 적용했다.
- focus/visibility 중복 요청과 한 학생의 조회가 다른 학생들의 과거 정산까지 반복하던 경로: 동일 요청 병합·대기 간격·요청 학생 범위 정산으로 수정했다.

일반 기록은 학생이 실제 제출한 원래 요청만 자동 복구한다. 금융·차감·삭제·교사 정산은 결과 조회만 자동화한다. 사용자·날짜·문항이 바뀌거나 실제 충돌이 나면 자동 재실행하지 않는다. 기기 보관 실패 시 작성 내용은 메모리에 유지되며, 복사 및 이탈 보호가 제공된다.

## 검증 근거

- `verify:release` 12단계 모두 통과: 타입 검사, 단위/API, 서버 실행, PostgreSQL 저장/보상/낱말 SQL, HTTP, 배포용 서버 런타임, 복구 훈련, 운영 빌드, 브라우저, 전체 앱 통합.
- 전체 단위/API 테스트: **1,189 / 1,189** 통과. 최종 운영 보호 기본값을 추가한 후 관련 **93 / 93** 테스트와 타입 검사 통과. 서로 겹치는 테스트이므로 두 수치를 합산하지 않는다.
- 운영 모드 컴포넌트 브라우저 장애 시나리오 **17 / 17**, 페이지 오류 **0**.
- 실제 RootApp 운영 빌드 + 인증 쿠키 + 실제 API + 로컬 PostgreSQL 통합 **5 / 5**, 페이지 오류 **0**.
- 서버 저장 직후 응답을 유실시키고 브라우저를 재실행해도 편지 **1건**, 영수증 **1건**. 학생 2의 기존 기록 보존, 학생 23명 잔액 유지, 원장 대조 불일치 **0건**.
- 최종 빌드를 브라우저에서 직접 조작해 학생의 보낸 편지와 교사의 같은 편지 조회를 확인했다. 1280×650, 1280×600, 1280×800의 충돌 복구 주요 동작은 브라우저 게이트에서 접근성과 화면 경계를 검증했다.
- 23학생 동시 요청 합성 재현에서 정산 RPC는 552회에서 46회로 감소했다. 이는 운영에서 측정한 트래픽 수치가 아니다.

전체 릴리스 검증의 소스 해시: `e5d9db73eda0f42dd1ccd405828132b15a77a2a616e606ad6c7ed4d1a9dfad23`. 이후 변경은 최종 보호 기본값과 그 테스트뿐이며 별도 93개 테스트로 검증했다.

근거 파일은 이 폴더의 `release-gate/`, `browser-gate/`, `full-stack-gate/`에 보관했다. 운영 함수 변경 전 정의는 `production-function-before.json`, 적용 SQL은 `production-classword-function.sql`에 있다.

## 확인 범위와 한계

운영 로그를 읽기 전용으로 조사했고 실제 운영 DB·Vercel에 변경을 적용했다. 2026-09-09 14:48:05 UTC 기준 최근 15분 저장 오류 수신·발생 건수는 모두 0건이었지만, 이 짧은 관찰만으로 다음 수업의 장애 부재를 보장할 수는 없다.

장애 주입과 23명 동시 저장은 실제 코드·인증·PostgreSQL을 사용하는 격리 합성 학급에서 수행했다. 학교 Wi-Fi나 실제 학생 계정에 고의 장애를 주입하지 않았다. 운영 오류 코드만으로 원래의 모든 서버·연결 장애 원인을 확정할 수는 없다. 기존 빌드의 큰 청크 경고 등은 남아 있지만 검증 실패는 없다.

새 보호 기능은 새 클라이언트를 불러온 뒤 사용된다. 이미 열려 있는 구버전은 위험한 저장 시 업데이트 안내를 받는다. 기존 미확인 요청은 먼저 영수증을 확인하며, 작성 내용과 요청 ID를 보존한다.
