# 2026-09-21 접속 장애 점검

## 운영에서 확인한 내용

- 실제 사이트 `https://school-timer-five.vercel.app/`에 브라우저로 접속했다. 최초 관찰은 로딩 화면, 이후 기존 테스트 번호 화면으로 진입했다.
- 브라우저 콘솔에서 UTC 00:35:17.952, 00:35:44.694에 초기/후속 공유 기록 조회 `SHARED_API_HTTP_502`를 확인했다. 테스트 번호의 자동 미션 HTTP 400은 실제 학생 장애와 별개다.
- Vercel Logs 직접 접속은 `net::ERR_CERT_COMMON_NAME_INVALID`로 차단됐다. 인증서 검증을 우회하지 않았다. 502의 구체적인 서버 원인은 아직 확정하지 못했다.
- 운영 DB의 scoped read 관련 인덱스와 `jit=off`가 이미 적용돼 있었다. 조회 순간 장기 잠금 대기는 관찰되지 않았다.
- 운영 `storage_load_scope(jsonb)` 본문 MD5 `76d4f4df41789ed7e009156ea01dfe4c`는 이번 성능 시험의 수정 전 함수와 일치했다.

## 준비한 수정

- `supabase/storage_scoped_polling.sql`: `readVersion` 계산에 이미 조회한 `nodes`와 wallet 범위를 재사용한다. 같은 요청에서 recursive 범위 조회를 다시 실행하지 않는다. 응답 필드, 조회 범위, 버전 해시, 권한은 유지한다.
- `src/lib/deviceSessionClient.ts`: 등록/해제에도 15초 응답 제한을 적용한다. 기존에는 번호 선택 후 해당 요청에 시간 제한이 없어 대기가 계속될 수 있었다. 자동 재전송하지 않는다. 이번 실제 학생 장애가 이 경로였다는 증거는 없다.

## 반영 상태

운영 DB 변경, Git commit/push, 앱 배포는 하지 않았다. 프로젝트 AGENTS.md의 마이그레이션 사전 확인 규칙에 따라 DB 함수 반영은 사용자 확인 후 수행해야 한다. 앱 배포는 사용자 소유다. 이 측정은 로컬 합성 부하 결과이며 운영 25명 접속 성공을 보장하지 않는다. DB 반영 후 실제 조회 지연/502와 학생 진입을 다시 확인해야 한다.

## 사용자 승인 후 운영 반영

- 사용자의 `ㅇㅇ` 승인 후 Supabase 프로젝트 `dxibhawclfhoabfgwria`에 `reuse_scoped_read_version_nodes` 마이그레이션 적용 성공.
- `storage_load_scope(jsonb)` 함수 하나만 교체했다. 적용 직전에 이전 본문 MD5 일치를 검사했고, 다른 함수/데이터/권한은 변경하지 않았다.
- 반영 후 본문 MD5 `f93f11edf5a0293376f94ff27762dbf2`가 로컬 검증본과 일치한다. anon/authenticated 실행 불가, service_role 실행 가능을 재확인했다.
- 운영 DB에서 학생 범위 읽기 결과가 정상 scoped 형식이며 독립 metadata 함수와 readVersion이 일치했다. 학생 작성 내용/잔액은 결과로 출력하지 않았다.
- 운영 사이트를 새 브라우저 탭에서 열어 기기 등록 확인 → 테스트 학생 개요 진입을 관찰했다. 해당 확인 시 브라우저 error 로그는 없었다. 테스트 학생은 전체 조회 경로이므로 이것만으로 실제 학생 scoped 조회나 25명 동시 접속을 검증했다고 간주하지 않는다.
- 인증 요청 시간 제한을 포함한 앱 소스의 배포는 수행하지 않았다. 전체 학생 접속 복구 및 동시 저장 성공은 추가 현장 확인이 필요하다.

## 운영 25세션 직접 검증 및 추가 수정

사용자의 25명 복구 검증 요청에 따라 `production25ReadCheck.mjs --production-readonly`로 실제 Vercel API에 25개의 독립 쿠키 세션을 생성했다. 학생 번호 1~23과 1·2번의 추가 세션을 사용했다. 인증 외에는 `/api/shared-settings` GET만 호출했고, 보상/저장 API는 호출하지 않았다. 쿠키와 응답 내용은 파일이나 로그에 남기지 않았다.

### 추가 병목 제거 및 반영

운영 조회 실행 계획에서 실제 844행인 nodes 결과를 89,890행으로 추정하며, `storage_scope_keys`를 각 행마다 반복 실행하는 구간을 확인했다. 동일 함수 내 nodes 조회를 primary-key semi-join으로 바꾸고, scope key 생성은 같은 세 가지 규칙을 집합 연산으로 계산하도록 변경했다. 운영 데이터를 대상으로 읽기 전용 비교에서 응답의 양방향 JSON containment가 일치했다. 별도 합성 DB에서는 모든 23학생과 5개 경계 범위의 전체 응답 일치 및 권한을 다시 검증했다. 합성 HTTP 300건 오류 0.

승인된 조회 함수 최적화의 후속으로 `bound_scoped_read_plan_estimates` 마이그레이션을 적용했다. 이전 함수 해시 일치를 검사한 뒤 함수 하나만 교체했다. 최종 본문 MD5 `a436ec1bcefdba20ae6f1951fcf77287`, anon/authenticated 실행 금지 및 service_role 실행 허용 유지.
