# 2026-10-16 저장 오류 조사

## 교사 공용 설정 저장 경로

제공된 오류는 `/api/shared-settings`의 `STORAGE_SCOPE_VIOLATION`이다.
알림의 기능 이름은 학급 설정이며, 실제 command action은 포함하지 않는다.
따라서 아래 재현 원인과 운영 오류가 동일한지는 당시 조작 또는 서버 로그의 action으로 확인해야 한다.

`teacher.currency.adjust`에 음수 amount를 보내면 교사 차감 로직이 학생 경제 상태와 알림 편지도 변경한다.
그러나 기존 scope는 이 데이터를 읽기만 허용했다. 기존 학생 경제 상태가 있는 합성 데이터에서
일반 차감과 차감 대기 모두 HTTP 400 `STORAGE_SCOPE_VIOLATION`으로 재현했다.

수정은 음수 조정 대상 학생의 `/studentEconomy/<번호>`와 수신 편지만 쓰기 범위에 추가한다.
양수 지급, 잔액 직접 설정, 초기화의 쓰기 범위는 확장하지 않는다.
테스트는 지갑·예금·투자금 차감, 잔액 부족 시 대기, 동일 요청 재전송과 다른 학생 데이터 보존을 검증한다.

## 6번 학생 은행 거래

발생: 2026-10-16 09:29:34 KST.
요청 ID: `387d4be5-56c6-481d-816c-0875d5f1b236`.
`STUDENT_ECONOMY_CONFIRMATION_REQUIRED` / 원인 `STUDENT_ECONOMY_UPDATE_FAILED`만으로는
거래 종류, 서버 내부 원인, 실제 저장 여부를 판단할 수 없다. 이번 조사에서는 운영 DB에 접속하지 않았다.

운영 Supabase SQL Editor에서 다음 읽기 전용 조회로 해당 요청의 영수증 존재 여부와 처리 메타데이터만 확인할 수 있다.
거래 본문, 편지, 전체 학생 기록은 조회하지 않는다.

```sql
select actor_key, request_id, action, committed_at,
       result->>'applied' as applied
from public.storage_receipts
where actor_key = 'student:6:economy:6'
  and request_id = '387d4be5-56c6-481d-816c-0875d5f1b236';
```

영수증이 있으면 이 요청은 커밋되었다. applied는 거래 반영 여부를 나타낸다.
영수증이 없거나 조회가 실패하면 저장 완료로 처리하지 않는다.
새 요청 ID로 거래를 반복하지 말고 기존 요청 ID를 사용하는 확인·재시도 경로를 사용한다.
원인 규명에는 당시 은행 조작과 Vercel의 해당 시각 `/api/student-economy` 저장 진단 코드가 필요하다.

## 반영

소스 수정은 운영에 자동 반영되지 않는다. 운영 배포는 사용자가 직접 수행한다.
이번 수정에는 DB 스키마 변경이 없다. 이전 오류 알림 확인 처리는 거래 복구와 별개이다.
