# 25개 세션 저장·조회 검증 (2026-09-20)

## 수정과 확인 범위

- `src/server/requestRateLimit.ts`: 같은 공인 IP의 학급 사용자 25명이 각 10회/분을 사용할 수 있게 일반 경로의 합산 한도를 250회로 조정했다. 개인 한도는 10회로 유지한다. 개인 한도 초과 요청은 다른 사용자의 합산 예산을 소진하지 않는다. 인증 전 기기 등록의 합산 한도는 기존 120회다.
- 수정 전 코드를 별도 임시 파일에서 실행한 결과, 25명이 각 10회 요청하면 250건 중 120건 허용·130건 거절이었다. 수정 후 같은 조건은 250건 허용이다.
- `src/lib/studentEconomyClient.ts`: 거래 응답 유실 후 확정 영수증을 최대 3회 확인한다. 확인 사이에는 250~500ms, 500~750ms 분산 대기를 둔다. POST 재전송은 하지 않으며, 영수증 해시 확인과 actor 변경 방어를 유지한다. 확인 불가능한 저장은 성공으로 표시하지 않는다. 인증·권한·요청 제한 오류는 추가 조회를 중단한다.
- `tests/storage/concurrent24MixedBenchmark.ts`: 기존 24개 세션 모드에 `--25-sessions`를 추가했다. 학생 23명과 교사 세션 2개가 각각 조회·저장을 반복한다. 학생 수 자체를 늘리거나 기존 학생 번호 계약을 변경한 것은 아니다.

첨부 화면의 연결 실패가 위 IP 제한으로 발생했다는 증거는 없다. 고마 거래 API 자체는 이 제한 함수를 사용하지 않는다. 연결 실패 당시의 배포 버전·HTTP 상태·서버 로그·DB 대기 정보는 이번 작업에서 확인하지 않았다.

## 실제 HTTP + PostgreSQL 결과

임시 PostgreSQL 17.11, localhost:55449, 테스트 전용 DB, 합성 자료만 사용했다. 운영 데이터·서버에는 접근하지 않았다. 각 DB RPC에 가상 왕복 지연 200ms를 추가했다. 학생별 초기 잔액은 1,000고마이며 각 회차 10고마를 예금했다.

| 지표 | 결과 |
| --- | ---: |
| 동시 세션 | 25 |
| 세션별 반복 | 40회 |
| 조회 / 저장 | 1,000건 / 1,000건 |
| HTTP 오류 | 0건 |
| 조회 p95 / 최대 | 411ms / 598ms |
| 저장 p95 / 최대 | 1,055ms / 1,312ms |
| 실행 시간 | 49.098초 |
| 저장 영수증 | 1,000건 |
| 학생 최종 잔액 | 23명 각각 600고마 |
| 원장 불일치 | 0건 |

추가 HTTP 통합 테스트에서 25개 동시 저장 모두 200, 같은 지갑 경쟁, 동일 요청 중복 방지, 응답 유실 후 영수증 확인, 오래된 교사 저장 차단, 학생 데이터 격리를 확인했다. 학생별 변경 버전과 공유 변경 감지, DB 역할별 접근 제한도 통과했다.

실제 교실 Wi-Fi, 운영 DB 자원 제한, 서버리스 인스턴스 분산은 재현하지 않았다. 이 수치는 운영 25명 접속의 보장 또는 첨부 장애의 원인 확정이 아니다.

## 검증

- 변경 관련 클라이언트/요청 제한 테스트 17개 통과. 25개 병렬 거래의 영수증이 세 번째 조회에서 확정되는 경우에도 POST가 각 한 번만 전송되는 것을 확인했다.
- `npm run lint`, `npm run build`, `git diff --check` 통과.
- `npm test`: 1,328 통과, 1 실패, 1 skip. 실패는 수정하지 않은 `src/lib/studentMissionPresentation.test.ts`의 `1인 1역 카드는 배정된 역할 또는 오늘 역할 없음을 표시한다`이다. 별도 실행에서도 역할명 `칠판 전문가` 표시 기대가 실패했다. 이번 범위 밖이므로 수정하지 않았다.
- 운영 배포, 운영 SQL 적용, Git 커밋·푸시는 하지 않았다.

## 재현

`STORAGE_TEST_PG_MODULE`은 설치된 `pg` 드라이버의 `lib/index.js`, `STORAGE_TEST_PG_PORT`는 격리 DB 포트로 지정한다. DB에는 테스트용 `anon`, `authenticated`, `service_role` 역할이 필요하다. harness는 `storage_http_test_*` 이름의 DB만 생성한다.

```sh
node --import tsx --test src/lib/studentEconomyClient.test.ts tests/api/requestRateLimit.test.ts
node --import tsx --test tests/storage/httpHarness.test.ts
MIXED_ROUNDS=40 node --import tsx tests/storage/concurrent24MixedBenchmark.ts --scoped-polling --teacher-writes --25-sessions
```

사용자 배포 후에는 실제 적용 버전, 오류 진단 정보의 HTTP 상태·코드, 저장 p95 및 DB 대기를 확인해야 한다. 기존 `STORAGE_SCOPED_POLLING=1` 최적화는 관련 SQL 적용 여부를 확인한 환경에서만 사용한다. 운영 호스팅 리전과 DB 리전의 현재 상태는 별도 확인이 필요하다.
