# 학생 23명 + 교사 1명 동시 사용 검증

기준 소스 HEAD: `1dfcca9b`, 이번 작업의 미커밋 변경 포함. 운영 SQL은 사용자 승인 후 2026-09-16 적용 완료. Netlify 환경변수 설정과 사용자 소스 배포는 남아 있다.

## 확인한 부하 원인

1. 학생 shared-settings GET이 학급 전체 `studentLife/letters`를 DB에서 받아 Node 함수에서 본인 편지만 남겼다. 접속자 수만큼 불필요한 전송·JSON 직렬화·조립이 반복됐다. 이제 기존 mailbox selector로 DB에서 본인 수신·발신 편지만 선택한다. 책·실패 이야기·프로필 배정은 기존 공유 범위를 유지한다.
2. 개인 지갑·개인 게임 등 어느 한 학생의 변경도 전역 `updated_at`을 바꿔 다른 학생의 전체 재조회를 유발했다. 새 scoped metadata는 화면에서 읽는 리소스와 지갑의 revision으로 변경 버전을 계산한다. 다른 학생의 개인 저장은 재조회하지 않고, 공용 경매 변경·삭제는 모두 재조회한다. 타임스탬프가 같은 지연 커밋도 revision 변경으로 감지한다.
3. 2026-09-16 02:31:43 UTC 운영 응답의 `x-school-function-region`은 `us-east-1`. Supabase `School_Timer` 프로젝트는 `ap-northeast-2`다. 일반 저장은 영수증 확인 → 범위 조회 → 커밋 → 결과 조회의 네 번 순차 RPC를 수행하므로 지역 간 왕복이 누적된다. 이번 수정에서 쓰기·영수증·잔액 잠금 계약은 변경하지 않았다.

관측된 운영 DB 누적 통계는 2026-08-06 이후 누적값이며 현재 장애 시점의 측정치가 아니다. scoped read 평균 350ms, 최대 약 7.97초였으나, 이것만으로 현재 CPU 부족 또는 잠금 대기를 유일한 장애 원인으로 단정하지 않는다. 읽기 전용 단일 활동 표본에서는 대기 쿼리가 없었다. 지역 확인용 HTTP 401은 정상 인증 거절이며 학생 접속 성공을 검증한 것이 아니다.

## 변경 파일과 활성화 방식

- `api/shared-settings.ts`: 학생 읽기 범위 축소, 서명 세션의 학생 번호로 scoped metadata 선택.
- `src/server/storageV2Repository.ts`: 변경 버전과 metadata 응답 검증.
- `src/lib/supabaseSettings.ts`: 학생 스냅샷의 변경 버전 기억, 같으면 전체 재조회 생략. actor 변경·저장 캐시 무효화 후에는 재확인. 미확인 저장을 성공으로 처리하지 않는다.
- `supabase/storage_scoped_polling.sql`: 기존 scoped read와 동일한 조회 결과에 `readVersion` 추가. 새 metadata RPC는 리소스 본문·내역 없이 버전만 반환한다. 기존 테이블 데이터와 쓰기 RPC는 수정하지 않는다. `SECURITY DEFINER`, 고정 `search_path`, `jit=off`, service_role 전용 실행 권한을 유지한다.

학생별 버전은 프로세스 메모리 TTL 캐시에 의존하지 않는다. 각 DB 조회에서 동일한 MVCC 스냅샷의 실제 revision을 계산하므로 Netlify 인스턴스가 여러 개여도 작동한다. 전체 수정 시각과 revision은 저장 확인·응답 순서 판정을 위해 그대로 보존한다.

`STORAGE_SCOPED_POLLING=1`이 Functions 환경에 설정된 경우에만 새 metadata RPC를 사용한다. SQL 미적용 또는 기능 플래그 미설정 상태에서는 기존 전역 metadata 경로를 유지한다. SQL만 먼저 적용해도 구형 클라이언트·서버는 추가 필드를 무시할 수 있다. **SQL 적용 전에 플래그를 켜면 안 된다.**

## 전후 비교

운영 학생 자료를 사용하지 않았다. 실제 PostgreSQL 17, 실제 HTTP API, 합성 편지 1,300개·지갑 내역 3,289개를 사용했다. PostgreSQL 요청과 응답에 각각 100ms, 합계 200ms의 가상 왕복 지연을 넣었다. 이는 운영 지연 측정값이 아니다.

24개 독립 세션이 5회씩 전체 조회하고 학생 23명은 매회 10고마를 예금했다. 학생마다 초기 잔액 1,000고마, 최종 잔액 950고마와 원장을 확인했다. 교사는 같은 기간 전체 화면을 읽었다. 전후 모두 120회 조회·115회 저장, 오류 0건이다.

| 지표 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 조회 p95 | 2,998ms | 566ms |
| 저장 p95 | 1,209ms | 1,079ms |
| 전체 실행 시간 | 14,019ms | 6,911ms |
| DB RPC 응답 전송량 합계 | 128.13MB | 55.58MB |
| 누락·중복 차감 / 원장 불일치 | 0 / 0 | 0 / 0 |

수정 전 측정은 소스 수정 전에 실행했다. 수정 후 수치에는 새 SQL의 revision 계산 비용을 포함한다. 전체 조회를 강제하는 스트레스 조건이므로 scoped metadata로 재조회를 건너뛰는 이득은 이 표에 포함되지 않는다. 최초 실행의 잘못된 합성 데이터 크기·예금 단위로 실패한 시도는 성능 비교에서 제외했다.

## 24명 혼합 지속 부하

학생 23명과 교사 1명 모두 조회와 저장을 80회씩 수행했다. 학생은 각자 10고마 예금, 교사는 안내 설정 변경이다. 네트워크 지연은 위와 같다.

- 약 96.36초, 조회 1,920건 + 저장 1,920건.
- 조회 p50 271ms / p95 347ms / 최대 636ms.
- 저장 p50 914ms / p95 1,015ms / 최대 1,145ms.
- HTTP 오류 0건, 영수증 1,920건, 학생 23명 최종 잔액 각각 200고마, 원장 불일치 0건.
- 이어서 개인 저장 1건은 해당 학생만 버전 변경, 공용 경매 리소스 삭제는 23명 모두 변경 감지.
- 전역 시각을 증가시키지 않은 revision 변경도 감지.

실제 운영의 24명 수용을 보장하는 결과는 아니다. 로컬 장비의 CPU·메모리, 단일 Node 프로세스, 모의 통신 지연 조건이다. Netlify 인스턴스 분산·운영 DB 리소스 제한·교실 Wi-Fi·각 Chromebook 렌더링은 재현하지 않았다. 운영에 부하나 테스트 저장을 보내지 않았다.

## 운영 적용 순서

1. 완료: 사용자 승인 후 Supabase에 `supabase/storage_scoped_polling.sql` 적용. 데이터 삭제·수정은 없다. 적용 대상은 조회 함수 세 개다.
2. 사용자가 Netlify Functions 환경변수에 `STORAGE_SCOPED_POLLING=1` 설정. 기존 `STORAGE_PROTOCOL_VERSION=2` 유지.
3. 가능한 요금제라면 사용자가 Functions 리전을 DB에 가까운 지역으로 변경한 뒤 소스를 배포. Netlify 공식 문서의 Functions region 지원 여부를 확인한다: https://docs.netlify.com/build/functions/configuration/#region
4. 배포 후 `x-school-function-region`으로 실제 지역 확인. 새 클라이언트의 학생 metadata 요청 `?metadata=1&scoped=1`이 HTTP 200과 `readVersion`을 반환하는지 확인.
5. 수업의 실제 24명 사용 중 shared-settings와 저장 API의 오류율·p95, 502/499 발생 시간 및 DB 대기를 관찰. 저장 테스트를 위해 실제 잔액이나 입찰 기록을 임의로 변경하지 않는다.

되돌리기: Functions 플래그를 제거하고 사용자 재배포하면 전역 polling으로 복귀한다. DB 조회 함수까지 되돌릴 경우 기존 `supabase/storage_scope_read_performance.sql`을 다시 실행한다. 새 보조 함수는 서비스 역할 전용으로 남겨도 기존 데이터·쓰기 경로에 영향이 없다. 복원 동등성은 격리 DB에서 검증했다.
