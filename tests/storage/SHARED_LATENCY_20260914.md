# 2026-09-14 여러 기능의 지연 재점검

## 운영에서 확인한 내용

- 최근 2시간 오류 집계: 주간 보상 network 24건·502 22건·504 3건, 고마 거래 확인 504 17건, 입찰 확인 502 4건 등 여러 API에 걸쳐 발생했다. 오류 알림의 집계이며 전체 요청 대비 오류율은 아니다.
- DB는 서울(`ap-northeast-2`)이고 `storage_load_scope`의 `jit=off`는 이미 적용돼 있었다.
- 누적 scoped RPC 5,782회, 평균 242.5ms, 최대 7,938.4ms. 코드의 DB 요청 제한은 8초다. 이 누적 통계 전부를 이번 장애 구간으로 해석할 수 없다.
- 점검 순간에는 활성 쿼리·잠금 대기가 없었다. 단일 scoped 함수의 읽기 전용 측정은 43.1ms였다. 동시 접속 시의 서버·DB 용량과 네트워크 지연은 아직 분리해 입증하지 못했다.
- 조회 내부에서 학생 장부를 얻기 위해 장부 테이블 전체를 순회하는 계획을 확인했다. 대상 학생의 인덱스를 쓰는 대안도 읽기 전용으로 비교했다. 반복 측정은 기존 25.0/22.5ms, 대안 20.7/19.7ms였다. 처음 측정한 231.3→27.6ms만으로 개선 폭을 주장하지 않는다. 운영 함수·SQL·데이터는 변경하지 않았다.

## 이번 소스 변경

- `AuctionPage.tsx`: 첫 학생 기록을 읽기 전에는 보상 API를 실행하지 않는다. 초기 확인을 기기별 1.5~4초로 분산하고, 기록 조회가 미완료면 다시 기다린다. 보상 확인 뒤에는 변경 시각부터 확인해 불필요한 전체 조회를 피한다. 숨김·오프라인 상태의 예약 실행도 중지한다.
- `netlify/functions/api.mts`: 모든 API 구현을 서버 시작 시 한꺼번에 초기화하던 부분을 요청 경로별 동적 import로 변경했다. 기존 인증·쿠키·라우팅을 유지한다.
- `storageRequestTiming.ts`, `storageV2Repository.ts`: 요청별 `Server-Timing`에 앱 처리 시간과 공통 storage RPC 누적 시간을 추가했다. RPC 횟수만 표시하며 학생 번호·본문·SQL·비밀키는 넣지 않는다. 다른 요청의 측정치는 섞이지 않는다.
- 런타임이 유효한 AWS 지역을 제공하면 `X-School-Function-Region`에 반환한다. 값이 없으면 헤더를 생략한다. 지역 설정 자체를 변경한 것은 아니다.

`storage` 시간은 `storageV2Repository` RPC만 포함한다. 다른 기능의 직접 PostgREST 요청과 플랫폼의 함수 준비 시간은 포함하지 않는다. 병렬 RPC 시간은 합산되므로 앱 시간보다 클 수 있다. 이 값 하나로 전체 DB 지연을 단정하지 않는다.

## 로컬 검증

- esbuild로 번들한 실제 어댑터를 새 Node 프로세스에서 5회 실행했다. 세션 없는 정상 401 경로의 초기 import+처리 중앙값은 기존 약 44.1ms, 변경 후 약 16.1ms였다. Netlify의 실제 cold start 측정은 아니다.
- 실제 학생 브라우저+분리된 HTTP 서버에서 초기 전체 조회를 4초 지연했다. 전체 조회 시작→종료 4,003ms 뒤 보상 API가 실행됐고, 전체 조회는 1회로 유지됐다. 모의 기록 표시와 로딩 종료를 확인했다.
- 로컬 HTTP 어댑터의 인증된 metadata 요청: 200, `app;dur=35.3`, `storage;dur=6.2`, `1 RPC`. 지역 헤더는 모의 환경변수로 검증했으며 운영 지역 확인 결과가 아니다.
- 회귀 검사: 첫 조회 대기, 오프라인 예약 취소, 정상 복귀, metadata 우선 확인, 요청 간 측정 격리, 인증·쿠키·라우팅.
- production build 통과. 타입 검사는 기존 `src/lib/studentPet.test.ts:204` TS2740 오류로 실패하며 이번 변경 파일의 추가 오류는 없다.

## 운영 확인에 필요한 항목

1. Netlify `Project configuration → Build & deploy → Continuous deployment → Functions region`의 실제 값을 확인한다. 이 값은 아직 확인되지 않았다.
2. DB는 서울이다. Netlify 공식 문서는 기본 지역을 Ohio(`cmh`)로 안내하고, DB와 가까운 지역을 사용할 것을 권고한다. 지원 목록에는 Tokyo(`nrt`)가 있으며 지역 선택은 Pro/Enterprise 기능이다. 요금제 변경이나 지역 변경은 수행하지 않았다.
3. 사용자가 수정본을 배포하고 학생 기기를 새로고침한 뒤, 느린 `/api/shared-settings` 응답의 상태·총 소요 시간·`Server-Timing`·지역 헤더를 같은 요청에서 확인한다. 쿠키·요청 본문은 공유하지 않는다.
4. `storage` 자체가 길면 같은 시각 DB의 CPU·활성 연결·쿼리 시간을 조사한다. 짧은 `storage`에 비해 전체 응답이 길면 함수 실행 지역·콜드 스타트·학교 네트워크를 함께 확인한다. 어느 경우든 미확인 저장을 삭제하거나 성공 처리하지 않는다.

공식 근거: https://docs.netlify.com/build/functions/configuration/#region (2026-09-14 확인).

운영 배포·DB 마이그레이션은 실행하지 않았다. 현재 운영 장애의 해결 완료를 선언할 수 없으며, 위 지역과 배포 후 요청 측정이 필요하다.
