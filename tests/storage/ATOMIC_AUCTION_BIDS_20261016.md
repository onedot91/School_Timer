# 동시 입찰 개선: DB 내부에서 입찰 경쟁 판정

## 단 하나의 변경 원리

입찰 충돌 시 서버가 조회→비교→저장을 반복하던 경로를,
DB가 최신 입찰·예약 잔액을 잠금 안에서 확인하고 한 번에 저장하는 경로로 변경했다.
화면·입찰 규칙·타임아웃·서버 크기는 변경하지 않았다.

서버는 기존 정규화·공개일·권한 검증을 수행하고, DB는 실제 저장 직전에
최신 최고가·중복 가격·낙찰 여부·여러 물품의 예약 잔액을 다시 판정한다.
설정 자체가 바뀐 경우에만 새 설정을 읽어 재시도한다.
영수증·학생 지갑·정렬된 범위 잠금 순서를 기존 저장과 동일하게 유지한다.

## 변경 전후 첫 측정

실제 임시 PostgreSQL, 학생 23명·교사 1명, 물품 6개, 합성 실패 글 69개,
과거 내역 2300개, DB 호출당 합성 지연 40ms인 동일 시나리오다.

| 항목 | 기존 CAS 경로 | 원자 입찰 경로 |
| --- | ---: | ---: |
| 입찰 p95 | 3250ms | 681ms |
| 입찰 최대 | 3274ms | 732ms |
| 전체 시나리오 DB 호출 | 277 | 117 |
| 전체 시나리오 CAS 충돌 | 80 | 0 |
| 재전송 후 상태 동일 | true | true |

p95 약 79% 감소다. 실행 순서에 따라 정상적인 낮은 입찰 거절 수는 달라질 수 있다.
같은 최종 최고가·낙찰 차감·과거 기록 보존과 잔액/원장 정합성을 별도로 검증한다.
로컬 합성 부하 결과이며 운영 지연을 측정한 결과는 아니다.

## 필수 검증

- 실제 API부터 PostgreSQL까지 같은 요청 재전송 및 커밋 후 응답 유실을 검증한다.
- 같은 학생의 서로 다른 물품 동시 입찰에서도 예약액이 지갑을 초과하지 않아야 한다.
- 초기 조회 이후 발생한 더 높은 입찰·낙찰을 저장 직전에 반영해야 한다.
- 설정 변경과 겹친 요청은 새 설정을 읽어 안전하게 재시도해야 한다.
- 교사의 학생 대리 입찰, 원자 입찰 이후 기존 저장 경로, JSON 리소스 키 호환성을 검증한다.
- 원자 입찰 RPC는 service_role만 호출하며 일반 학생·anon·authenticated에는 실행 권한을 주지 않는다.
- SQL 재적용이 다른 함수 본문을 바꾸지 않아야 한다.
- 필수 부하 검사에서 원자 입찰 p95 2초를 초과하면 빌드를 차단한다.

## 운영 반영 순서

1. Supabase SQL Editor에서 `supabase/storage_command_round_trips.sql`을 실행한다.
   테이블·학생 데이터 삭제 없이 기존 두 RPC 정의를 유지하고 원자 입찰 RPC와 순수 변환 함수를 추가한다.
2. Vercel 서버 환경변수 `STORAGE_ATOMIC_AUCTION_BIDS=1`을 설정한다. `VITE_` 접두어를 붙이지 않는다.
3. 사용자가 변경된 소스를 직접 배포한다. 기존 버전은 이 변수를 사용하지 않는다.

변수가 없거나 `0`이면 기존 경로를 사용한다. 새 경로를 켠 상태에서 RPC가 없거나 오류가 나면
성공으로 처리하거나 구형 쓰기로 자동 재전송하지 않는다. 같은 요청 ID의 영수증 확인 경로를 유지한다.
필요하면 변수만 `0`으로 돌린 버전을 사용하여 기존 경로를 선택할 수 있고, 추가 SQL 함수를 삭제할 필요는 없다.
