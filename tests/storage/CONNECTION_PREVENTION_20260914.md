# 2026-09-14 접속 장애 재발 방지

## 수정 범위

- 학생 설정 조회가 연속 실패하면 자동 재시도를 5·10·20·40·60초 기준으로 늦춘다. 각 대기에 최대 20%의 무작위 지연을 더하고 서버의 더 긴 `Retry-After`를 우선한다.
- 주기 조회도 기기별로 분산한다. 일반 화면은 10~12초, 경매는 2~2.4초다. 숨겨진 화면과 오프라인 상태에서는 주기 조회하지 않는다.
- 화면 복귀·저장 후 새로고침 요청도 실패 대기를 지킨다. 진행 중인 요청은 공유하며, 연달아 예약된 전체 조회는 한 실행에서 최대 두 번 처리한다.
- 초기 오류 화면의 사용자 `다시 시도`는 즉시 조회할 수 있다. 조회 성공 후 실패 횟수와 대기 시간을 초기화한다.
- 자동 주간 보상 확인의 두 API도 연속 실패 시 대기를 늘린다. 요청 공유, 성공 후 5초 대기, 서버 `Retry-After`, 저장 실패 보고는 유지한다.
- 실패한 조회를 빈 기록으로 적용하지 않는다. 미확인 저장을 성공으로 처리하거나 보관 중인 요청을 삭제하지 않는다.

주요 파일: `src/pages/AuctionPage.tsx`, `src/lib/studentSettingsSync.ts`, `src/lib/weeklyMissionClient.ts`.
DB 스키마·운영 환경변수·배포는 변경하지 않았다.

## 사용자 배포 후 확인

1. 사용자가 새 소스를 배포하고 학생 기기의 화면을 새로고침한다. 이전에 열린 화면은 이전 요청 간격으로 계속 실행될 수 있다.
2. 처음에는 소수 기기에서 조회를 확인한 뒤 실제 수업 인원으로 확대한다. 실제 학생 계정에서 반복 거래·보상 지급을 부하 시험으로 실행하지 않는다.
3. 같은 10분 구간의 `/api/shared-settings`, `/api/weekly-missions`, `/api/weekly-mission`, `/api/student-economy`를 각각 확인한다. 요청 수, 499·429·5xx 수, 응답 시간 p95를 기록한다. 전체 사이트 성공률에는 정적 이미지 요청이 섞이므로 API별로 본다.
4. 초기 운영 확인 기준은 API 5xx 1% 미만, 조회 응답 p95 2초 이내로 둔다. 이는 검증된 실적이 아니라 점검 목표다. 5xx가 반복되거나 p95가 5초를 넘으면 동시 사용 확대를 멈추고 같은 시간대 Functions 오류와 DB CPU·활성 연결·조회 시간을 비교한다.
5. 과부하가 남으면 DB 실행 계획·서버 처리 용량을 별도로 점검한다. 조회 제한 시간을 늘리는 것만으로 해결했다고 판단하지 않는다. 새로고침 반복이나 미확인 요청 삭제로 오류를 지우지 않는다.

이 변경은 장애 중 요청 폭증을 억제한다. 운영 인프라나 학교 네트워크 장애까지 무장애를 보장하지 않으며, 배포 후 관측으로 추가 용량 조정 필요 여부를 판단해야 한다.
