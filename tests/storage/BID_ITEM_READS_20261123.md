# 학생 화면: 입찰 기록을 물품별로 다시 읽기 (2026-11-23)

## 문제

2026-11-23 09:30 수업에서 DB가 멈추기 직전(09:32), 학생 변경분 읽기가 분당 94건으로 가장 많았고 같은 1분에 입찰이 9건 있었다.
로컬 PostgreSQL에서 다른 학생의 저장이 내 읽기 버전을 바꾸는지 확인했다.

- 감정·숫자야구·동그라미 저장: 바뀌지 않는다. 숫자야구·동그라미는 첫 기록 때만 바뀌며 보낼 내용은 없다.
- 입찰: 바뀐다. 접속한 학생마다 학급 전체 입찰 기록을 다시 받는다.

입찰이 없던 시각에도 변경분 읽기가 있었다. 이 변경은 멈춤의 유일한 원인을 고치는 것이 아니다.

## 변경

- `supabase/storage_manifest_range.sql`: `storage_scope_selector_manifest`가 경로 접두사 색인을 쓴다. 결과는 이전과 같다.
- 서버(`STORAGE_BID_ITEM_READS=1`일 때만): `X-Storage-Bid-Items: 1`을 보낸 학생의 읽기 범위에서 `/auctionBidHistory` 하나를 물품 30개로 나눈다.
  폴링도 `bidItems=1`일 때 같은 범위를 비교한다. 헤더가 없는 이전 화면과 변수가 꺼진 서버는 기존 경로다.
- 다른 배치의 요약은 거절하지 않고 무시해, 변수를 켜고 끌 때 열려 있던 화면은 그 부분만 한 번 다시 받는다.

## 측정 (로컬, 합성 자료 3,525행, 물품 10개에 입찰 기록 1,200건을 고르게 나눔, 12회 중앙값을 3회 반복)

| 경우 | 이전 | 이후 |
|---|---:|---:|
| 입찰 1건 뒤 변경분 읽기 | 21.5~21.7ms, 534KB | 12.8~12.9ms, 58KB |
| 바뀐 것 없음 | 12.0~12.3ms, 2.5KB | 11.9~12.1ms, 4.6KB |
| 버전 계산(폴링) | 5.5~5.6ms | 6.0~6.4ms |
| SQL 없이 물품별로만 나눈 경우, 바뀐 것 없음 | 12.0~12.3ms | 20.0~20.3ms |

마지막 줄 때문에 SQL을 먼저 적용해야 한다. 기록이 한 물품에 몰리면 효과가 줄어든다. 운영 효과는 측정하지 않았다.

## 운영 반영 순서

1. Supabase에 `supabase/storage_manifest_range.sql` 적용. 함수 본문이 예상과 다르면 중단한다.
2. 코드 배포.
3. Vercel Production 환경변수 `STORAGE_BID_ITEM_READS=1` 후 재배포.

되돌리기: 변수를 `0`으로 바꿔 재배포한 뒤, 필요하면 `supabase/storage_manifest_range_rollback.sql`을 적용한다.
