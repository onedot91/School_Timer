## 확인된 원인과 한계

2026-09-29 08:45~10:00 KST 범위를 Supabase 로그에서 집계했다.
09:30~09:39에 5초를 초과한 DB API 응답 94건이 집중됐으며,
해당 범위 PostgreSQL 로그에는 쿼리 취소 코드 `57014`가 63건 있었다.
취소된 작업에는 `storage_load_scope` 27건, `storage_load_snapshot` 17건,
`storage_load_scope_metadata` 8건 등이 포함됐다.

Vercel 로그에서도 09:38 전후 설정 조회·저장 결과 확인 요청에
`STORAGE_DATABASE_TIMEOUT`, 약 8,000ms, HTTP 502가 함께 기록됐다.
DB 응답 지연이 애플리케이션의 8초 제한을 넘긴 사실은 확인됐다.
DB 대시보드에 swap 사용과 I/O wait 증가가 보였으나,
과금 등급·디스크 제한·실행 계획 중 무엇이 지연을 유발했는지는 확정하지 않았다.
현재 정상 상태가 당시 장애가 없었다는 뜻은 아니다.

화면의 08:58:43 교사 설정 오류는 별도의 HTTP 409다.
해당 시간대 DB API 평균 응답은 약 31ms였으므로 위 09:30대 지연과 같은 사건으로 단정할 수 없다.
당시 저장된 진단에 세부 오류 코드가 없어서 정확한 충돌 원인은 소급 확정할 수 없다.
코드에서 `TEACHER_SETTING_CONFLICT`와 `RESOURCE_REVISION_CONFLICT`가 진단 허용 목록에서
빠진 것을 확인하고 두 코드만 추가했다. 원본 오류나 학생 작성 내용을 수집하지 않는다.

## 소스 수정

- 오류 알림 조회 제한: 5초에서 12초. 서버의 단일 DB 요청 제한 8초에 응답 전달 여유를 둔다.
- 오류 알림 전송 제한: 8초에서 12초. 전송 실패 시 기존 대기열 보존 동작을 유지한다.
- 개별 확인 처리 제한: 8초에서 20초. 서버의 조회·수정 두 단계에 맞춘다. 일괄 확인은 기존 20초를 유지한다.
- 교사 설정·오류 알림 자동 조회: 실패 시 대기 시간을 5, 10, 20, 40, 60초까지 늘린다.
  숨긴 탭과 오프라인에서는 자동 조회를 멈추고, 표시 상태로 복귀하면 다시 조회한다.
  성공하면 정상 주기로 돌아간다. 오류 알림의 수동 재조회는 대기 시간을 건너뛴다.
- 기록 저장, 중복 지급 방지, 충돌 보호, 저장 결과 확인 절차는 유지한다.

## 운영 반영 후 확인

수정은 아직 운영에 배포되지 않았다. 저장소 정책에 따라 운영 반영은 사용자가 수행한다.
배포 후 수업 동시 접속 구간의 DB 응답 시간, `57014`, Vercel `STORAGE_DATABASE_TIMEOUT` 발생률을
다시 비교해야 한다. 이번 변경은 조기 조회 실패와 장애 중 반복 요청을 줄이며,
DB 부하 자체가 완전히 해소됐다고 보장하지 않는다.

지연이 계속되면 조회 쿼리의 실행 계획과 해당 시간대 메모리·I/O 지표를 함께 확인한 후
쿼리 최적화 또는 리소스 조정을 결정한다. 유료 전환이나 운영 스키마 변경은 별도 승인 대상이다.
