## 서버 오류 처리 수정 및 한계

이하 문제는 합성 응답으로 재현한 코드 결함이다. **오전 Vercel 장애의 원인이 이 결함이었다고 확정한 것은 아니다.**

- 공용 저장소가 HTTP 상태 확인 전에 응답을 JSON으로 파싱했다. HTML 503·빈 502는 원래 상태를 잃었고, 저장 후 손상된 성공 응답은 은행·설정 API에서 `400 INVALID_BODY`로 잘못 분류됐다. 이제 `502 STORAGE_INVALID_RESPONSE` 또는 원래 upstream 상태가 포함된 `STORAGE_DATABASE_HTTP_*`로 구분한다.
- 네트워크 거절·시간 초과는 안정적인 저장소 오류 코드로 구분한다. 도서관의 기존 응답 유실 복구도 이 코드로 계속 작동하게 연결했다.
- 낱말장의 네트워크·본문 수신·JSON 실패를 내부 코드 오류 500과 구분해 502로 처리한다. 실제 내부 오류의 500, 정상적인 업무 거절, 204·빈 본문 계약은 유지한다.
- 은행·공용 명령의 최종 서버 실패는 경로·단계·상태·허용 코드·소요 시간, 낱말장 실패는 경로·상태·허용 코드를 남긴다. 복구된 충돌과 업무 거절은 오류 로그를 남기지 않는다. 학생 내용·원문 오류·쿠키·키는 기록하지 않는다.
- 거래 재전송을 추가하지 않았다. 저장 결과가 불명확하면 기존 영수증 확인 절차를 사용한다. 서버 경고 제거, 장애 원인 확정, 운영 재발 방지 완료를 주장하지 않는다.

주요 파일: `src/server/storageV2Repository.ts`, `src/server/storageFailureDiagnostics.ts`, `src/server/storageCommandHandler.ts`, `src/server/libraryCompetitionService.ts`, `src/server/classwordRepository.ts`, `api/student-economy.ts`, `api/classword.ts`.

## 코드상 방지책

- 초기 임시 저장소 조회와 편집의 경합, 저장 확인 후 남는 경고를 회귀 테스트로 보호한다.
- 다른 탭의 늦은 조회 결과가 더 최신 편집·확인 결과를 덮어쓰지 않도록 검사한다.
- 최종 임시 보관 실패만 기존 저장 오류 보고 경로로 수집한다. 대기 중이거나 같은 저장 큐에서 복구된 실패는 신고하지 않는다.
- 저장소 종류, 저장·교체·정리 작업, 허용된 원인 코드와 오류 유형, 요청 ID, 소요 시간을 남긴다. 원문 오류·작성 내용·저장 키·entity ID는 수집하지 않는다.
- 같은 기능·저장소·작업·원인은 1분 동안 중복 보고하지 않는다. 실제 미보관 입력의 새로고침 보호와 내용 복사는 유지한다.
- 고마 거래의 미확정 오류는 최초 오류 원인, 요청 ID와 영수증 확인 횟수를 유지한다. 진단을 위해 거래를 재전송하지 않는다.

## 재발 시 확인 순서

1. 작성 중 화면을 유지한다. 임시 보관 경고가 있으면 내용을 별도로 보존하고, 사이트 데이터 삭제·반복 거래 실행은 하지 않는다.
2. 교사 저장 오류에서 **진단 정보 복사**를 누른다. 코드, 발생 시각, 배포 버전, 요청 ID, 실패 단계, 저장소와 작업 종류를 확인한다.
3. `LOCAL_DRAFT_QUOTA_EXCEEDED`: 기기 공간·사이트 저장 제한 확인. `LOCAL_DRAFT_ACCESS_DENIED`: 브라우저 저장 권한 확인. `LOCAL_DRAFT_DATABASE_BLOCKED`: 다른 탭의 DB 버전 변경 차단 여부 확인. `LOCAL_DRAFT_CAS_CONFLICT`: 다른 탭의 입력과 비교하되 현재 내용을 먼저 보존한다.
4. 서버 오류는 발생 직후 Vercel 프로젝트 Logs에서 같은 시각 전후 5분의 요청과 경로·허용된 오류 코드·시간·단계를 대조한다. 현재 확인한 플랜의 개별 로그 보존 범위를 넘기기 전에 안전한 진단 필드만 확보한다. 학생 본문, 쿠키, 인증 헤더는 공유하지 않는다. 오래된 보고에 요청 ID가 없으면 일대일 대응을 확정하지 않는다.
5. 응답 미확정은 영수증·실제 기록부터 확인한다. 알림 확인 처리는 기록 복구가 아니며, 운영 배포는 사용자가 수행한다.

로그가 추가된 버전 이후의 재발부터 더 상세히 판별할 수 있다. 저장 공간 고갈, 연결 단절 등 외부 요인까지 재발하지 않는다고 보장하지 않는다.

## 검증

- 늦은 탭 조회가 최신 편집을 덮는 경우와 확인된 초안을 되살리는 경우를 수정 전 실패·수정 후 통과로 확인했다.
- 용량 부족 원인, 민감정보 제외, 1분 중복 억제, 저장 대기·같은 큐에서 복구된 오류 제외, 경제 요청의 원인 보존, 진단 API 저장·조회 회귀 테스트를 통과했다.
- `npm run lint`, `npm test`(1,366 통과·0 실패·1 제외), `npm run build`를 통과했다.
- 로컬 mock 브라우저에서 실제 오류 알림 컴포넌트와 임시 보관 실패를 연결해 확인했다. 1280×650·600·800에서 진단 펼침, 내부 스크롤, 키보드 버튼 접근, Escape·포커스 복귀를 검증했다. 콘솔 오류는 없었다.
- 오류 안내의 한글 단어 단위 줄바꿈을 보정했다. 새 패키지 설치, 운영 데이터 변경, 운영 배포는 수행하지 않았다.
- 실제 화면 7개에 대한 독립 기능·디자인 검토와 한글·시각 검토 모두 PASS였다. 임시 QA 진입점·브라우저 탭·로컬 서버는 검증 후 정리했다.

### 서버 수정 후 추가 검증

- 수정 전 은행·설정은 저장 1회 후 응답 손상 시 실제로 `400 !== 502` 테스트 실패. 수정 후 502로 구분되고 영수증 `200 committed`로 확인된다.
- 낱말장 오류 경계는 수정 전 24개 중 10개 실패, 수정 후 관련 70개 통과. 저장소·도서관 관련 32개도 통과했다.
- 최종 `npm test`: 1,388개 중 1,387 통과, 실패 0, 실제 PostgreSQL 연결 조건이 없는 연동 테스트 1개 제외. 별도 `src/server/storageV2Repository.test.ts` 3개 통과.
- `npm run lint`, `npm run build`, `git diff --check` 통과.
- 실제 로컬 HTTP 서버에 `curl`로 POST했다. 은행·설정 각각 `502 STORAGE_INVALID_RESPONSE`, 이어지는 영수증 GET 각각 `200 committed`. 합성 저장 횟수는 합계 2회로 중복 실행이 없었다. 낱말장도 `502 CLASSWORD_DATABASE_INVALID_RESPONSE` 확인. 로그에는 허용된 진단 필드만 나타났다.
- HTTP 검증은 운영과 같은 API 핸들러·세션 검증에 합성 세션과 로컬 저장소 대역을 연결했다. 운영 Vercel 장애나 실제 Supabase 장애를 재현한 검증은 아니다. UI 변경은 없으며, 임시 HTTP 서버와 소스는 검증 후 정리했다. 배포는 사용자가 수행한다.
