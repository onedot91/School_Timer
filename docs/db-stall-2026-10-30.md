# 수업 중 DB 정체 조사 (2026-10-30)

운영 데이터와 설정은 바꾸지 않았다. 읽기 전용 조회와 로그를 사용했다.
단, 11:12 KST 수업 중 운영에서 30.9초짜리 읽기 측정을 한 번 실행해 그 시각 정체를 키웠을 수 있다.
이후 운영 측정은 중단하고 로컬에서 재현했다.

## 증상

10:47, 10:50, 11:10~11:13 KST에 Vercel `icn1`에서 `STORAGE_DATABASE_TIMEOUT`(약 8초, 502),
`SHARED_SETTINGS_READ_FAILED`, `REWARD_AUDIT_SOURCE_TIMEOUT`이 났다. 학생 입찰도 8초 후 실패했다.

## 확인한 사실

- 정체 구간에는 거의 모든 요청이 함께 느려졌다. 키 하나로 찾는 `storage_get_receipt`도 0.8~3.2초였다.
  잠금 대기 하나가 아니라 DB 전체가 느려졌다.
- 10:47·10:50은 분당 약 30건으로 부하가 낮았지만 무거운 읽기 여러 개가 2~3초 안에 겹쳤다.
  11:10 수업 시작 뒤에는 분당 약 200건으로 늘었다.
- 11:10~11:40 Supabase API 시간 합계 상위:

| 호출 | 건수 | 중앙값 | 합계 |
|---|---:|---:|---:|
| `storage_load_scope_student` (학생 화면 전체 읽기) | 144 | 418ms | 162초 |
| `storage_get_receipt` (저장 확인, 가벼운 조회) | 267 | 47ms | 153초 |
| `app_settings` | 413 | 21ms | 116초 |
| `storage_poll_scope_student` (학생 주기 확인) | 595 | 24ms | 98초 |
| `gugudan_*` (같은 DB를 쓰는 구구단 앱) | 89 이상 | — | 68초 이상 |

- 입찰 기록 묘비는 15개다. 10/26 정리 일정이 매일 성공해 그때 원인은 재발하지 않았다.
  학생 편지(`studentLife`) 묘비는 805개로 10/26의 708개보다 늘었다.
- Supabase 조직이 Free 요금제라서 DB는 가장 작은 Nano 컴퓨트(공유 CPU, 메모리 최대 0.5GB)다.
  설정은 `shared_buffers` 224MB, `max_connections` 60, `work_mem` 2.1MB다.

## 배제한 원인: 정렬 메모리(`work_mem`)

쿼리 통계에는 학급 전체 읽기와 보상 점검이 임시 파일을 쓴 기록이 있어 `work_mem` 부족을 의심했다.
로컬 PostgreSQL에서 운영과 같은 함수, 같은 `work_mem` 2.1MB, 운영 크기 합성 데이터(스냅샷 8.9MB, 원장 13,800행)로 쟀다.

| 로컬 | `work_mem` 2.1MB | 16MB |
|---|---:|---:|
| 학급 전체 읽기 직접 호출 | 101ms | 101ms |
| 학급 전체 읽기 PostgREST 형태 | 108ms | 108ms |
| 보상 점검 PostgREST 형태 | 135ms | 128ms |

2.1MB에서는 보상 점검만 10MB 임시 파일을 썼고 시간 차이는 거의 없었다. PostgREST 감싸기 비용도 약 7ms다.
운영에서 잰 1,393ms → 583ms 차이와 30.9초는 수업 부하와 겹친 값이다. 메모리 조정은 해결책이 아니다.

## 원인

같은 학급 전체 읽기가 로컬은 약 100ms, 운영 DB는 1.3초다. 운영 DB의 CPU 여유가 매우 작다.
수업 시작 때 학생 기기들이 한꺼번에 읽고(학생 전체 읽기 중앙값 418ms), 교사 읽기·보상 점검·같은 DB의 구구단 앱이 겹치면
CPU가 포화되고 가벼운 조회까지 8초 제한을 넘긴다. 학생 읽기 동시 2개 제한(10/23)과 보상 점검 1개 제한(10/26)이 있어도 남는다.

## 선택지

1. **DB 컴퓨트 올리기(Nano → Small)**: 코드 변경 없이 CPU·메모리를 늘린다. Supabase 요금이 늘어난다. 사용자가 결정한다.
   아래 "컴퓨트 올리기 검토"를 본다.
2. **학생 전체 읽기 줄이기**: 수업 시작 때 학생 화면이 받는 범위를 줄이거나, 변경분만 받게 한다. 효과 측정이 필요하다.
3. **구구단 앱 부하 분리**: 같은 DB를 쓰므로 수업 시간에 같이 쓰면 서로 느려진다.

## 컴퓨트 올리기 검토

Supabase 문서(Compute and Disk, Manage Compute usage) 기준. 요금은 USD이며 바뀔 수 있다.

| 컴퓨트 | CPU | 메모리 | 최대 연결(직접) | 컴퓨트 요금(월) |
|---|---|---|---:|---:|
| Nano (현재, Free) | 공유 | 최대 0.5GB | 60 | 0 |
| Micro | 2코어 ARM 공유 | 1GB | 60 | 약 $10 |
| Small | 2코어 ARM 공유 | 2GB | 90 | 약 $15 |
| Medium | 2코어 ARM 공유 | 4GB | 120 | 약 $60 |
| Large | 2코어 ARM 전용 | 8GB | 160 | 약 $110 |

- Nano 외의 컴퓨트는 Pro 요금제(월 $25)가 필요하다. Pro에는 Micro 1개 분량인 월 $10 컴퓨트 크레딧이 들어 있다.
  - Pro + Micro: 약 $25/월
  - Pro + Small: 약 $30/월 ($25 + $15 − $10)
  - Pro + Medium: 약 $75/월
- 같은 조직의 프로젝트는 요금제를 함께 쓴다. 구구단 앱이 같은 프로젝트(DB)를 쓰므로 둘 다 혜택을 받는다.
- Nano~Medium은 짧게 높은 성능을 내고(버스트) 여유가 소진되면 기본 성능으로 돌아간다. 수업처럼 몇 분씩 몰리는 부하에서는 기본 성능이 중요하다.
- 컴퓨트 변경 시 DB가 재시작된다. 보통 2분 이내 중단. 수업이 없는 시간에 한다.
- Pro로 올려도 Nano가 자동으로 바뀌지 않는다. 요금제를 올린 뒤 컴퓨트를 직접 고른다.
- Pro는 기본으로 지출 상한(Spend Cap)이 켜져 있다.

### 결정 (2026-10-30)

사용자가 Free 요금제를 유지하기로 했다. 컴퓨트는 Nano 그대로 두고, 코드로 수업 중 DB 부하를 줄이는 쪽(선택지 2·3)으로 간다.
아래 권장과 절차는 나중에 다시 검토할 때를 위한 기록이다.

### 권장 (보류)

Pro + Small(약 $30/월). 메모리가 Nano의 4배이고 CPU도 공유 2코어로 커진다. Medium 이상은 CPU 형태가 같아 먼저 Small의 효과를 본다.
효과는 장담하지 않는다. 다음 수업에서 같은 지표로 비교한다.

### 절차 (요금·결제는 사용자가 직접)

1. Supabase 대시보드 → 조직 Billing → Pro로 업그레이드(카드 등록).
2. 수업 없는 시간에 프로젝트 `School_Timer` → Settings → Compute and Disk → Small 선택 → 확인(약 2분 중단).
3. 변경 뒤 확인: 프로젝트 상태 `ACTIVE_HEALTHY`, DB 설정값(`shared_buffers`, `max_connections`), 운영 사이트 응답.
4. 다음 수업에서 비교: 11:10~11:40과 같은 구간의 학생 전체 읽기 중앙값(현재 418ms), 57014 건수, `STORAGE_DATABASE_TIMEOUT` 건수.

## 학생 화면 읽기 측정 (2026-10-30 수업 후)

### 운영 크기 (5번 학생, 응답 길이만 측정)

학생 전체 읽기 한 번의 응답은 **1,287KB**다.

| 항목 | 크기 |
|---|---:|
| 본인 입출금 기록 전체 | 433KB |
| 경매 입찰 기록 | 233KB |
| 실패 게시판(학급 전체) | 135KB |
| 주간 과목(`weeklySubjects`) | 127KB |
| 학급 역할 미션 | 97KB |
| 주식 시장 | 83KB |
| 그 밖 | 약 180KB |

- 입출금 기록은 학생 평균 386행이고, 그중 최근 14일은 103행(27%)뿐이다. 7월부터 쌓여 학년 말까지 계속 커진다.
  교사 화면은 이미 최근 14일만 읽는다(`storage_teacher_history_window.sql`).
- 학생 화면은 기록을 목록으로 보여 주지 않는다. 오늘·이번 주 보상 여부 확인(`hasDailyEmotionReward`, `hasDailyWritingReward`, `hasWeeklyMissionReward`)에 쓴다.

### 다시 읽는 빈도

학생 화면은 주기 확인(`storage_poll_scope_student`)에서 자기 읽기 범위가 바뀌었다고 나오면 **전체(1.3MB)를 다시 읽는다**
(`shouldLoadFullStudentSettings`). 범위에 경매 입찰·실패 게시판·역할 미션 같은 학급 공용 자료가 들어 있어,
누가 입찰하거나 도장을 찍으면 학생 23명이 모두 1.3MB를 다시 읽는다. 11:10~11:40 학생 전체 읽기는 144회였다.

### 로컬 재현 (합성 데이터, 응답 2MB)

학생 전체 읽기 35.6ms. 시간은 응답 크기에 거의 비례했다. 기록만 7ms, 지워진 편지 772개를 없애도 1ms 차이다.

### 줄이는 방법 (효과 큰 순서)

1. **바뀐 부분만 다시 읽기**: 교사 화면처럼(`changes=1`, 읽기 목록 비교) 바뀐 자료만 받는다. 입찰 한 번에 1.3MB 대신 몇 KB가 된다. 작업이 가장 크다.
2. **학생 입출금 기록을 최근 기간만 읽기**: 433KB → 약 120KB(최근 14일 기준). 학년이 지날수록 차이가 커진다. 보상 확인에 필요한 기간을 먼저 확인한다.
3. **주간 과목을 이번 주만 읽기**: 127KB 중 대부분. 수업 준비 배너가 쓰는 범위를 먼저 확인한다.
