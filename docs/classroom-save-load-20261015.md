# 동시 저장 검증 · 2026-10-15

`npm run test:storage:load`로 재현한다. 운영 서버에 연결하지 않고 임시 Unix 소켓 PostgreSQL과 실제 `/api/shared-settings` 핸들러를 사용했다. 교사 1명과 학생 23명이 동시에 시작하며, 학생은 경매 입찰 후 실패 기록을 저장한다. 합성 실패 글 69건, 타 학생의 도장, 학생별 통화 내역 100건, 월요일 경매 물품 6개, RPC당 지연 40ms를 사용했다.

| 지표 | 수정 전 | 최종 실행 1 | 최종 실행 2 | 최종 실행 3 |
| --- | ---: | ---: | ---: | ---: |
| 교사 설정 저장 성공 | 1/1 | 1/1 | 1/1 | 1/1 |
| 실패 기록 저장 성공 | 23/23 | 23/23 | 23/23 | 23/23 |
| 입찰 저장 충돌 한도 초과 | 12/23 | 0/23 | 0/23 | 0/23 |
| 입찰 정상 접수 / 낮은 가격 거절 | 6 / 5 | 14 / 9 | 14 / 9 | 11 / 12 |
| 실패 기록 p95 | 3,398ms | 326ms | 326ms | 464ms |
| 교사 설정 응답 | 194ms | 230ms | 259ms | 239ms |
| 입찰 p95 | 1,767ms | 4,058ms | 6,736ms | 5,921ms |

수정 전 입찰 응답에는 조기 실패가 포함되므로 짧은 응답 시간을 개선 성과로 해석하지 않는다. 최종 반복 실행의 입찰 최대 응답은 7,579ms였다. 실행 순서·경합·로컬 CPU 부하에 따라 입찰 접수 수와 응답 시간이 달라진다.

실패 글 저장 시 본인과 관련된 글을 먼저 찾고 해당 글만 완전히 읽는다. 조회 사이에 도장을 찍은 다른 글이 추가되면 재시도하고, 선택자 한도를 넘는 경우 전체 조회로 복귀한다. 쓰기 권한은 본인 범위로 유지한다. 입찰에는 통화 내역을 읽지 않으며 잔액의 버전 검사는 유지한다. 동시 입찰의 충돌 재시도는 최대 24회로 늘리고 대기 증가를 제한했다. 다른 저장의 재시도 한도는 5회다.

최종 실행은 기존 글·도장 보존, 실패 글 23건과 학생별 보상 15, 최신 입찰자 6명의 낙찰 차감, 성공 요청 재전송 시 중복 차감·보상 없음, 원장과 잔액 일치를 확인했다. 검증용 재전송과 낙찰은 위 부하 응답 시간 집계에서 제외했다.

최종 실행 3에서는 기존 통화 내역 2,300건 보존까지 확인했다. 타입 검사와 빌드 통과, 기본 테스트 1,539건 통과·기존 1건 건너뜀, 실제 PostgreSQL 회귀 2건 통과·건너뜀 없음으로 검증했다.

로컬 `psql` 프로세스 실행 비용을 포함한 측정이다. Vercel 인스턴스 분산, 운영 데이터 크기, 실제 네트워크 및 Supabase 지연은 재현하지 않았으며, 운영 장애가 해소됐다고 단정할 수 없다. 배포와 운영 DB 변경은 수행하지 않았다.
